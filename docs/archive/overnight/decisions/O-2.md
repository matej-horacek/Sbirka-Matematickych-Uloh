# O2 — Notifications for copy holders

Status: **Open**. Not decided by this document.

## Current state

- **Runbook §6 (Open), quoted:** "`updateAvailable` is decided (computed on read). Still open: the `updateProblem` description says copy holders "are notified". Does that mean only the flag, or also stored notification rows? Older notes planned notifications."
- **Runbook §6 (Decided), quoted:** "`updateAvailable` is **computed on read, not stored**; the author acts on it with `take-over-update` or `dismiss-update`."
- **Spec 2.0.0:** `updateProblem`: "Editing a set child also raises the set's version (copy holders of the set are notified)". `ProblemListItem.updateAvailable`: "Computed on read, not stored." `UpdateAvailableFilter`: "With limit=1, meta.total is the badge count." There is no notification resource, endpoint or schema in the spec.
- **Mock:** neither part exists (R-007). The mock stores `originalProblemId` + `originalProblemVersion` on each copy (`mock-database.ts` `ProblemRow`), which is enough to compute the flag.
- **Tests:** only the decided part is tested (skipped, `copies/update-available.e2e-spec.ts`); stored notifications are untested by design.

## Options

### A. "Notified" = the computed flag only (documentation wording)
The badge is `GET /problems?scope=mine&updateAvailable=true&limit=1` → `meta.total`. No notification table.
- **Pros:** already fully specified; no new table, endpoint, or write on every edit; matches "computed on read".
- **Cons:** no history ("what changed and when"); no notifications for anything other than copies; the frontend must poll the badge.
- **Spec:** reword "are notified" to "see `updateAvailable`" (doc-only change).
- **Mock:** R-007 only.
- **Tests:** unchanged; the skipped T4.4 tests cover it.
- **Phase B:** one indexed comparison per copy (copy.original_version vs original.version, minus a dismissed version). Nothing stored on edit.

### B. Flag + stored notification rows (event log)
Each applied edit of an original writes a `notification` row per copy holder; a new `GET /notifications` (+ mark-read) lists them. `updateAvailable` stays computed.
- **Pros:** history and a general notification channel (later also review results, moderation); push-friendly.
- **Cons:** fan-out write on every edit (a popular problem with many copies → many rows); two sources of truth for "has an update" (row vs flag) that can disagree; new endpoints to spec and secure.
- **Spec:** new `Notifications` tag, `GET /notifications`, `POST /notifications/{id}/read` (sketch below).
- **Mock:** new module `notifications` (repository, service, controller); `ProblemsService.update` (and child edits, take-over of sets) must emit.
- **Tests:** new operation tests + store checks "edit of an original creates N rows".
- **Phase B:** new Prisma model; writes inside the edit transaction or via an outbox/queue.

### C. Flag now, notification rows deferred to a later phase
Spec keeps only the flag (as A) and the "are notified" wording is replaced with a forward reference ("a notification feed is planned").
- **Pros:** unblocks 2.0.0 and Phase B with no extra scope; leaves the door open.
- **Cons:** wording promises something unscheduled; if B comes later, existing copies need backfilling.
- **Spec / mock / tests:** as A now.
- **Phase B:** as A; B's table can be added later without changing `updateAvailable`.

## Sketch (option B, not applied to the spec)

```yaml
  /notifications:
    get:
      operationId: listNotifications
      tags: [Notifications]
      description: |
        Who: any logged-in teacher; only their own notifications, newest first.
      parameters:
      - $ref: '#/components/parameters/Page'
      - $ref: '#/components/parameters/Limit'
      - {name: unread, in: query, schema: {type: boolean}}
      responses:
        '200': {content: {application/json: {schema: {$ref: '#/components/schemas/NotificationPage'}}}}
        '401': {$ref: '#/components/responses/Unauthorized'}

    post:
      operationId: markNotificationRead

      responses:
        '200': {content: {application/json: {schema: {$ref: '#/components/schemas/Notification'}}}}
        '401': {$ref: '#/components/responses/Unauthorized'}
        '404': {$ref: '#/components/responses/NotFound'}
```
