# O3 — PDF export

Status: **Open**. Not decided by this document.

## Current state

- **Runbook §6 (Open), quoted:** "Client-side printing was decided, but older notes plan a BullMQ + Redis + Puppeteer export queue."
- **Spec 2.0.0:** no export endpoint. The only PDF-related field is `SourceRef.showInPdf` (boolean, per problem source), i.e. the data model already anticipates a printed form in which a source can be hidden.
- **Mock:** nothing beyond storing and returning `showInPdf` (always `true` for new problems, `problems.service.ts:101`).
- **Stack (§6 Decided):** NestJS, PostgreSQL, R2 for images, Docker. Redis/BullMQ is not in the decided stack.
- **Tests:** nothing to test; no operation exists.

## Options

### A. Client-side printing only (as decided)
The frontend renders a worksheet (KaTeX/MathJax) with a print stylesheet; the user prints to PDF in the browser.
- **Pros:** no server component, no Redis, no headless Chrome in Docker; instant; the spec stays as it is.
- **Cons:** output depends on the browser (page breaks, fonts); no server-side archive or share link of a PDF; large worksheets rely on the client.
- **Spec:** none. **Mock:** none. **Tests:** none (frontend e2e if anything).
- **Phase B:** none. `showInPdf` is applied by the frontend print view.

### B. Server-side export queue (BullMQ + Redis + Puppeteer)
`POST /exports` enqueues a job; a worker renders the page in headless Chrome and stores the PDF in R2; the client polls `GET /exports/{id}`.
- **Pros:** identical output everywhere; PDFs can be cached, shared, archived; heavy work off the client.
- **Cons:** two new infrastructure pieces (Redis, a worker with Chromium, about 300 MB image); job lifecycle and error states; another auth surface (who may download which PDF); much more to defend at the maturita.
- **Spec:** new `Exports` tag, 2 operations (sketch below), 202 Accepted pattern.
- **Mock:** a fake queue (instant "done") would be enough for the frontend.
- **Tests:** operation tests + job-state tests; Puppeteer rendering needs an integration environment.
- **Phase B:** adds Redis to docker-compose, a worker process, R2 upload. Could slip into Phase C+.

### C. Synchronous server render, no queue
`GET /problems/{id}/pdf` (or a worksheet endpoint) renders on request with Puppeteer and streams the PDF.
- **Pros:** consistent output without Redis/BullMQ; simple contract.
- **Cons:** request time grows with document size; headless Chrome per request needs a pool and limits (DoS risk); still the Chromium image.
- **Spec:** one operation returning `application/pdf`. **Phase B:** Chromium in the API image.

## Sketch (option B, not applied to the spec)

```yaml
  /exports:
    post:
      operationId: createExport
      tags: [Exports]
      description: |
        Who: any logged-in teacher, for problems they can see. Starts a PDF export job.
      requestBody:
        content: {application/json: {schema: {type: object, required: [problemIds],
          properties: {problemIds: {type: array, maxItems: 100, items: {$ref: '#/components/schemas/Sqid'}}}}}}
      responses:
        '202': {description: Job accepted, content: {application/json: {schema: {$ref: '#/components/schemas/ExportJob'}}}}
        '400': {$ref: '#/components/responses/BadRequest'}
        '401': {$ref: '#/components/responses/Unauthorized'}
  /exports/{id}:
    get:
      operationId: getExport
      description: Who: the job's creator. status QUEUED | RUNNING | DONE | FAILED; url is set when DONE.
      responses:
        '200': {content: {application/json: {schema: {$ref: '#/components/schemas/ExportJob'}}}}
        '404': {$ref: '#/components/responses/NotFound'}
```
