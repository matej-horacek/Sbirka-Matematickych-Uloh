# O5 — Marking auto-approved revisions

Status: **Open**. Not decided by this document.

## Current state

- **Runbook §6 (Open), quoted:** "How to mark one is undecided. `moderation_log.actor_id` is meant for admins only. Automatic actions may go to a separate table."
- **Runbook §6 (Decided), related:** "untrusted verified teachers go through review on first publish and on edits to published content; trusted teachers and admins publish directly."
- **Spec 2.0.0:** no revisions or moderation endpoints. Visible effects only: `updateProblem` (and the `/children` operations, takeOverUpdate) answer **202** when the change waits for review; `publishProblem` gives `REVIEWING` for a verified teacher, `PUBLISHED` for trusted/admin.
- **Mock:** no revisions at all. `problems.service.ts:131-133` returns 202 and stores nothing (`TODO Phase B: store the change as a problem_revision waiting for review`, B3); `publication.module.ts:7` (B5) "revisions and review (problem_revision, approve/reject)". A trusted edit is applied in place (B4: `minor_version` planned).
- **What "auto-approved" means here:** a trusted teacher's (or admin's) publish/edit that would be a revision for others, but is applied directly. The question is whether, and where, that event is recorded.
- **Tests:** nothing to test tonight (no API surface). Noted in `actions/publish.e2e-spec.ts`.

## Options

### A. `problem_revision` row with an approval marker, no moderation_log entry
Every applied change creates a `problem_revision` (also for trusted users), with `status = APPROVED`, `approved_by = null`, `approval = AUTO` (enum `MANUAL | AUTO`).
- **Pros:** one place holds the full history of content changes, manual or automatic; `moderation_log` stays "admin actions only" as intended; easy query "what went live without review".
- **Cons:** a revision row per trusted edit (storage, but revisions are planned anyway); `approved_by` nullable needs care in queries.
- **Spec:** none (internal). **Mock:** none tonight.
- **Phase B:** `problem_revision` gets `approval_kind` and nullable `approved_by_id`; the publish/update services write it in the same transaction.

### B. Separate `system_action_log` table for automatic actions
`moderation_log` = admin decisions (actor_id NOT NULL → users). New `system_action_log(problem_id, revision_id, action, reason, created_at)` for auto-approvals and future automatic actions (auto-block, etc.).
- **Pros:** keeps both logs strict (no nullable actor); matches the runbook hint "automatic actions may go to a separate table"; extensible for other automatic actions.
- **Cons:** two logs to read for a full audit trail; one more table and model.
- **Spec:** none. **Phase B:** one more Prisma model; written next to the revision.

### C. `moderation_log` with a nullable actor (or a system user)
`actor_id = NULL` (or a seeded "system" user) for automatic approvals.
- **Pros:** one log, one query for the moderation history.
- **Cons:** contradicts the stated intent ("actor_id is meant for admins only"); a system user pollutes the users table and permission checks; NULL actor weakens the FK meaning.
- **Spec:** none. **Phase B:** schema change on `moderation_log`.

No spec sketch: none of the options changes the API.

## What I'd look at first
Whether trusted edits should create a `problem_revision` at all (B4's `minor_version` suggests in-place edits), since A depends on that.
