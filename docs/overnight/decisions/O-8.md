# O8 — Version bump

Status: **Open** (Daniel fixes it himself). Not decided by this document.

## Current state

- **Runbook §6 (Open), quoted:** "`info.version` is still `1.0.0` although the changelog describes 2.0.0. Report it in `SPEC_CHECK.md`; Daniel fixes it himself."
- **Spec:** `openapi.yaml:21` `version: 1.0.0`; `openapi.yaml:9` changelog top entry "2.0.0 (2026-10-29): block model".
- **Reported:** `SPEC_CHECK.md` C-1 and S-list (under Open).
- **Knock-on effects found tonight:**
  - generated code (`@hey-api/openapi-ts`) and `/docs` (Scalar) show "1.0.0" for a 2.0.0 contract;
  - the mock still implements 1.0.x (R-002..R-011), so a client reading `info.version` would wrongly conclude the server matches;
  - the server URL stays `/api/v1` (path versioning), independent of `info.version`.

## Options

### A. Set `info.version: 2.0.0` (semver of the contract)
- **Pros:** matches the changelog; 2.0.0 really is breaking (`children` removed, a code renamed), so a major bump is semantically right.
- **Cons:** none for the contract. Frontend/backend must agree on the bump moment (the mock is not 2.0.0 yet).
- **Spec:** one line. **Mock / tests:** none (the tests read operations, not the version). **Phase B:** none.

### B. Set `2.0.0` and add a version check to the build
Same as A, plus a small check in `verify` that `info.version` equals the newest changelog entry.
- **Pros:** prevents this mismatch from happening again.
- **Cons:** another check to maintain (cheap: a 10-line script next to `scripts/check-spec-examples.mjs`).
- **Spec:** one line. **Tooling:** new script + a `verify` step.

### C. Keep the API path at `/api/v1` and `info.version` at the URL major (1.x), changelog as the detailed history
- **Pros:** URL major and `info.version` major stay aligned.
- **Cons:** contradicts the changelog's own numbering; a breaking change without a major bump makes `info.version` meaningless for clients.
- **Spec:** reword the changelog entry to 1.1.0, or accept the mismatch.

No sketch needed: option A/B is a one-line change (`version: 2.0.0`).

## What I'd look at first
Whether the frontend reads `info.version` anywhere (generated client headers, docs); if not, it only affects documentation.
